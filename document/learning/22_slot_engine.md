# 22_slot_engine: booking slots that can't be overbooked

> **Branch:** `22_slot_engine` · **Date:** 2026-10-28 · **Status:** In progress (ready for review)

## In one minute

The garage now has booking slots in its database: 1-hour slots inside opening hours, bookable from tomorrow up to 7 days ahead, never on a closed day, and never with more vehicles than a slot can take. Nothing on the site changes yet. Task 23's booking page will be the first thing to use it. The pieces:

- three new tables (slot rules, closed dates, places taken per slot);
- a pure function that lists the bookable days and slots, worked out on India's calendar;
- `reserveSlot`, `releaseSlot` and `moveSlot`, which each change a slot's count in **one** SQL statement, so two customers can't both take the last place.

Session 1 had task 16 and Session 2 had task 17. ## Why: the problem we solved

Booking (task 23) needs an answer to "which times can I offer?" and a guard on "take this time". Without a slot engine:

- the wizard would have nothing to show;
- two customers booking the last place at the same moment would both succeed (a **race**, see below);
- "tomorrow" could be worked out in UTC, and from 00:00 to 05:30 in India every night the site would offer same-day slots, which the owner doesn't take.

The owner decided the rules on 2026-10-28: **1-hour slots**, **book from tomorrow up to 7 days ahead**. The capacity (how many vehicles per slot) isn't decided yet, so it's a clearly labelled **placeholder of 2**, cars and two-wheelers together (`ownerSlotRules` in `src/server/db/seed-data.ts`).

   ```bash
   git fetch origin && git merge origin/main   # no conflicts this time
   npm install                                 # always after a merge
   npm run db:generate -- --name=slot_engine   # writes 0002_slot_engine.sql + meta/
   ```
   `--name` sets the file name after the number. The new tables sit after `opening_hours` in `schema.ts`, not at the end, so sessions appending their own tables don't hit the same lines.
7. **Check an existing database upgrades without a reset.** The dev server was started once *before* the migration existed (so `.pglite/` had the old schema), then again after:
   ```bash
   npm run dev -- --port 3002   # port 3002 is this session's; 3000 is Session 1's
   ```
   Reading the database afterwards showed 3 applied migrations, the 3 new tables and the rules row `{60, 2, 1, 7}`.
8. **U4: reserve, release, move** (`src/server/dal/slots.ts`). Reserve is one statement (simplified):
   ```sql
   insert into slot_counters (starts_at, reserved) values ($1, 1)
   on conflict (starts_at) do update set reserved = slot_counters.reserved + 1
   where slot_counters.reserved < $capacity
   returning reserved
   ```
   No row back means "full". Release subtracts 1 only `where reserved > 0`.
9. **Break each guard once on purpose** (a mutation check, see below) and watch its test fail. The results are under "Check that it works".
10. **Run everything:** `npm run check` and `npm run test:e2e`. `npm run test:design` wasn't run: nothing in the design changed, and its port (3000) belongs to Session 1.
11. **Review with `ce-code-review`** (seven reviewers plus a validator). Verdict: "Ready with fixes", nothing P0 or P1. Four findings were confirmed and fixed (see "Reviews").

## New ideas in this task

- **Race condition:** two requests read "1 place left" at the same moment, and both take it. Like two people grabbing the last seat because both saw it empty.
- **Atomic conditional update:** one SQL statement that checks and changes together (`... where reserved < capacity`). Postgres locks the row while it writes. A second writer waits, then re-checks the condition against the new value. No gap means no race.
- **Upsert** (`insert ... on conflict do update`): insert a row, or update it if it already exists. The counter row is created by the first reservation.
- **Transaction handle:** the booking task opens a transaction, then passes it (`tx`) to `reserveSlot`. The booking and its place then commit or roll back together. `moveSlot`'s type accepts only a transaction, because it's two statements.
- **Row lock** (`select ... for update`): "I'm changing this booking, wait your turn". Later tasks lock the booking row before cancelling or rescheduling, so a double click can't give a place back twice.
- **India date vs UTC date:** a date is a calendar day somewhere. 29 Oct in India begins at 18:30 UTC on 28 Oct. The code never asks the computer for "today"; it asks `Intl` for India's date.
- **Mutation check:** break the code on purpose and make sure a test fails. A test that still passes when the code is wrong guards nothing.
- **Idempotent seed:** running it twice changes nothing (`onConflictDoNothing`), so it can run on every start.

## Common mistakes

- **A parallel test that can't fail.** PGlite (the local database) runs one query, or one whole transaction, at a time. Five reservations each wrapped in `db.transaction` run one after another, so a racy reserve still looks correct. The test calls the bare database instead, so the calls interleave query by query. Even then it can't prove the real row race: task 20 runs it on a real Postgres.
- **Querying outside the open transaction.** On PGlite, `getDatabase()` (or the cached `readGarage()`) inside a transaction waits forever. Every slot read goes through the handle it's given.
- **Returning "full" after writing the booking.** Returning from a transaction commits it, so a booking without a place would be saved. Reserve first, then write.
- **Renaming a migration by hand** when another session's lands first. Drizzle only applies migrations newer than the last one a database applied. Session 2's `0002_vehicle_catalogue` is newer than this branch's `0002_slot_engine`. Whichever task merges second must delete its migration and run `db:generate` again, never rename it. `database.test.ts` now fails on an out-of-order timestamp.
- **A comment that disagrees with the code.** `checkSlotRequest`'s comment listed its checks in the wrong order; the review caught it.
