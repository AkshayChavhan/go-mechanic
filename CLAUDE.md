## The project

- **GoMechanic**: a website and booking system for **one garage in India** that repairs cars and two-wheelers. Features: `document/website/features.md`. Full plan, architecture and tasks 07–46: `document/plans/2026-10-24-gomechanic-master-plan.md` (approved by the owner).
- **Stack, installed (task 09):** Node 24 LTS (`.nvmrc`), Next.js 16.4.3 (App Router, Cache Components), React 19.3, TypeScript 5, Tailwind CSS 4, shadcn/ui 4 (Radix base, nova preset), GSAP 3.15, Vitest 5, Playwright 1.64; next-intl 4.14 (task 10: English now, Hindi-ready); fonts and design tokens (task 11: San Francisco on Apple devices, Inter elsewhere, Noto Sans Devanagari for Hindi, through `next/font`); the database (task 14: Drizzle ORM 0.45.4 and drizzle-kit 0.31.11, PGlite 0.5.9 locally, postgres.js 3.4.9 for a real Postgres); login (task 15: Better Auth 1.7.14 with its phone-number plugin, a fake SMS provider).
- **Stack, planned for later tasks:** Supabase Postgres and Vercel (20). SMS, WhatsApp and email use fake providers until the launch tasks (44–45).
- **Design:** Apple-like, calm and spacious, with smooth GSAP scroll animation (see "Design direction" in `features.md`). The design system is `design-system/go-mechanic/MASTER.md` (approved 2026-10-26; the site shell 2026-10-27); see it all at `/dev/design` under `npm run dev`. Version 1 has no online payments or GST invoices.
- **The owner is learning.** Every task must teach. Write explanations for a junior software engineer.

## Commands

Run them with Node 24 (`.nvmrc`; `fnm use` if your shell is on another version).

```bash
npm run dev          # dev server on http://localhost:3000
npm run check        # lint + typecheck (next typegen + tsc) + unit tests; must pass before every commit you call done
npm run test:e2e     # Playwright on a production build (port 3210, your installed Chrome); must pass before every merge
npm run test:design  # Playwright on /dev/design under next dev (port 3000; reuses a running dev server), saves screenshots to test-results/design/
npm run build        # production build
npm run lint         # ESLint only
npm run typecheck    # next typegen, then tsc --noEmit
npm run test         # Vitest once (npm run test:watch to keep it running)
npx shadcn@latest add <component>   # add a shadcn/ui component
npm run db:generate -- --name=<what_changed>   # after a schema.ts change: write its SQL migration
npm run db:reset     # delete the local database (.pglite/ and .pglite.lock); only while npm run dev is stopped
```

`test:e2e` isn't part of `check` because it needs a production build (slow). `test:design` first loads every page its specs visit (`e2e/dev/warm-up.ts`), so `next dev` never compiles a page while a test has another one open: add a new page to that list when a dev spec visits it. Never run `npx playwright install`: it downloads browsers; the tests use the Chrome already installed. If `typecheck` fails with an error inside `.next/dev/types/` after you moved a route, delete `.next/dev` (stale types from an earlier `npm run dev`) and run it again. If a CSS change doesn't show up in `npm run build` or `test:e2e`, delete `.next/cache/turbopack` (Turbopack's build cache) and run again: seen once in task 11, not reproduced in 3 later tries. A filtered Playwright run (`-g`, or one spec file) empties that config's output folder first, so the screenshots in `test-results/` exist only after a full `test:e2e` or `test:design`: run `test:e2e` before `test:design` (its folder holds the other), or copy the screenshots first.

## Code conventions

- **Next.js 16 is newer than your training data.** Before using a Next.js API, read its guide in `node_modules/next/dist/docs/` (see `document/solutions/conventions/nextjs-16-read-bundled-docs-image-priority.md`). Cache Components is on (`cacheComponents: true`).
- **Server Components by default.** Add `"use client"` only to components that need state, effects, event handlers or browser APIs, and keep them small.
- **Imports** use the `@/` alias (`@/lib/utils`).
- **Code layout** (from the master plan): `src/app/` routes, `src/components/{ui,site,account,admin}`, `src/domain/` pure logic with no Next.js or database imports, `src/server/` database, data access, actions and providers, `src/lib/` small helpers.
- **Tests sit next to the code:** `*.test.ts` runs in Node (logic), `*.test.tsx` runs in jsdom (React components). Browser tests go in `e2e/`. Import `test`/`expect` from `vitest` (no globals).
- **Tests run in UTC:** `TZ` in `vitest.config.mts`, `timezoneId` in `playwright.config.ts`. The owner's computer runs in IST, which would hide code that uses the computer's time zone instead of `Asia/Kolkata`. A test that needs another zone sets it itself.
- **Playwright and animation:** never fix the clock (`page.clock.setFixedTime`) while motion is on. It freezes `Date.now`, which GSAP times itself with, so no reveal would ever finish. Screenshots and content checks of animated pages use `reducedMotion: "reduce"` (GSAP never loads; the page is at rest) and may fix the clock; motion checks use the real clock. Playwright's `toBeVisible()` counts opacity 0 as visible, so check opacity (`effectiveOpacities` in `e2e/helpers.ts`).
- **Tailwind only scans `src/`, minus test files** (`source("../")` and `@source not` in `src/app/globals.css`). Put anything that uses Tailwind classes inside `src/`, and not in a `*.test.*` file.
- **Design system** (`design-system/go-mechanic/MASTER.md`; `globals.css` wins if they disagree):
  - Colours, radius, shadows and spacing only through token classes (`bg-card`, `text-link`, `rounded-xl`, `py-(--section-space)`). No raw values outside `globals.css` and `src/components/ui/`.
  - Text size comes only from `type-*` classes (Tailwind writes stock classes after them, so a stock class on the same element wins):
    - Banned: stock `text-*` sizes (lint rejects them), and `leading-*` or `tracking-*` next to a `type-*` class, except inside a component's own definition (such as Wordmark's tracking).
    - Allowed: a weight next to a `type-*` class (`type-callout font-semibold`, Button's `font-medium`). It wins, which is the point.
    - Never put two `type-*` classes on one element, so never pass a `type-*` class to a component that sets its own (Button, Card, CardTitle, CardDescription, Input): Tailwind's CSS order picks the winner, not your class order.
    - A `type-*` class passed to a component doesn't beat stock sizes the component sets itself. Badge, Sheet, Field and Label keep shadcn's sizes until a task restyles them, so change a component's size through its variant or size prop.
    - Lint misses arbitrary sizes (`text-[17px]`) and stacked `leading-*`/`tracking-*`: check those by hand.
  - Page sections use `Section` (`tone`: white, grey or dark; `width`). There is no site-wide dark mode.
  - Buttons and fields keep 44px touch targets. One blue (`default`) button per group.
  - The brand name lives only in `messages/en.json`; pages show it through `Wordmark` (`brand-name.test.ts` enforces it).
  - Motion timings come from `@/lib/motion`. GSAP animations go inside `gsap.matchMedia()` with `motionAllowed` and `motionReduced`, and content is visible before JavaScript runs.
  - Scroll motion goes through `ScrollScene`: sections mark their markup with `sceneMark(...)` from `scroll-scene-attributes.ts`, never with their own GSAP code. Only `scroll-scene-effects.tsx` (loaded lazily, in the browser, for visitors who allow motion) and dev pages import GSAP; `src/lib/gsap-imports.test.ts` fails otherwise. Never mark a link or a button, or anything around one, as a reveal target.
  - Sample content (made-up stats and reviews) shows only through `showSamples()` (`src/lib/samples.ts`): under `npm run dev`, never on staging or in production. Pages read it through the selectors in `src/content/` (`home.ts`, `about.ts`, `faq.ts`, all built on `realOrSamples()`), which prefer real data; each sample carries `data-sample` and a `SampleBadge`, and each file has a canary phrase that `e2e/home.spec.ts` and `e2e/info-pages.spec.ts` search production builds for. Keep `showSamples()` apart from `devOnly()`.
  - `/dev/design` is the living catalogue of the design. A task that adds or changes a token, a `type-*` style or a `ui/`/`site/` component also adds or updates its sample there, and `npm run test:design` must pass.
  - The site shell (header, footer, phone action bar, offer banner) lives in `src/components/site/` and wraps public pages through `src/app/[locale]/(site)/layout.tsx`. New public pages go under `(site)`; pages outside it (`/dev/design`, later `/admin` and `/login`) get no shell.
  - Keep public pages prerendered: never read cookies, headers or the time in the shell. Data comes through cached reads (`readGarage()` uses `'use cache'`). "Open now" is worked out in the browser (`OpenStatus`) for that reason. A login slot (task 15) goes in a `<Suspense>` or a client island. The home page exports `ensureStatic = "navigation"`, so a request-time read in it or in the `(site)` layout fails `next dev` and `next build` ("encountered uncached or runtime data on a route that must be fully static").
- **Development-only pages** live in `src/app/[locale]/dev/`, call `devOnly()` (`@/lib/dev-only`) first so production answers 404 with `noindex`, and may type demo text (lint allows it there only). Their metadata goes in a `generateMetadata` that also calls `devOnly()` first, never a static `metadata` export: a 404 thrown only from the page keeps the page's own title (`dev-only.test.ts` enforces it).
- **Languages (next-intl).** The site is English-only for now but must stay Hindi-ready:
  - UI text goes in `messages/en.json` and is read with `useTranslations`. Pages stay non-async unless they read data (`await readGarage()`): then they're async and read their text with `await getTranslations(...)`, since hooks don't work in async components. Their tests render `await Page()` with the data-access function and `next-intl/server` mocked (`(site)/page.test.tsx`). Other async server code (`generateMetadata`, layouts) uses `getTranslations` too. Lint rejects text typed into JSX in `src/app/` and `src/components/` (except `ui/` and dev pages): between tags, inside conditions (`{ok ? "Yes" : "No"}`, one level nested too) and in `alt`, `title`, `placeholder`, `aria-label`, `aria-description`, `aria-valuetext`, `aria-roledescription`, `aria-placeholder` and props named `label` or ending in `Label` (`closeLabel`, `openLabel`). `src/i18n/lint-guards.test.ts` keeps these rules working; add a case there for any new guard (`document/solutions/conventions/lint-guards-test-real-jsx-shapes.md`). Lint doesn't check page metadata, so put its text in messages too.
  - Client components (`"use client"`) get their labels as props from a server parent where possible (`MobileMenu`'s `openLabel`, `closeLabel`). Only the namespaces listed in `src/i18n/client-messages.ts` reach the browser, so a namespace a client component reads with `useTranslations` must be named (`useTranslations("OpenStatus")`, never `useTranslations()`) and listed there. `client-messages.test.ts` fails otherwise.
  - `Link`, `redirect`, `useRouter` and `usePathname` come from `@/i18n/navigation`, not `next/link` or `next/navigation` (lint enforces it), so the `/hi` prefix is kept.
  - Money is stored and passed as integer paise and shown with `formatRupees` (`₹1,23,456`). Dates and times are shown with `formatDate` and `formatTime`, always in India time (`Asia/Kolkata`). Format first, then pass the string to `t()`: don't use ICU `{n, number}` or `{d, date}` in messages, because next-intl formats those with plain `en` (`₹123,456`, US date order).
  - Text stored in the database is a `LocalizedText` (`{ en, hi? }`), shown with `localize(text, locale)`.
  - Route Handlers and Server Actions pass the locale explicitly (`getTranslations({ locale, namespace })`): there's no `[locale]` page around them.
  - Page slugs never contain a dot or start with `api`. The proxy skips paths starting with `api`, `_next` or `_vercel`, and paths ending in a file extension listed in `src/proxy.ts`, so such a page would miss the language handling. `src/proxy.test.ts` checks every file in `public/` and every metadata file in `src/app/`, so a real file is never sent through the proxy and 404'd: a new file type needs its extension in that list. Other dotted paths (old-site links like `/index.html`) get the branded 404.
  - Component tests render with `renderWithIntl` from `@/i18n/test-utils`.
- **Secrets** come from environment variables, read on the server only. Never prefix a secret with `NEXT_PUBLIC_`: those values are built into the JavaScript every visitor downloads. Add every variable to `.env.example` with a fake value.
- **Database** (task 14; plan `document/plans/2026-10-27-2221-feat-database-setup-plan.md`):
  - Which database runs where: `npm run dev` uses PGlite in `.pglite/` (kept between restarts). `next build`, `npm start`, `test:e2e` and Vitest use PGlite in memory, a fresh one per process with the owner's garage. `chooseDatabase` decides by `NODE_ENV` and `NEXT_PHASE`: a build always gets memory, even `next build --debug-prerender`, which builds with `NODE_ENV=development`. A `DATABASE_URL` (any mode) uses postgres.js. Local PGlite migrates and seeds itself on first use; the app never migrates or seeds a real Postgres (task 20 does that on purpose).
  - Queries live only in `src/server/dal/`. Pages and components call its functions and never import `@/server/db`. Every `src/server/` file starts with `import "server-only"` (a Server Actions file: `"use server"` first, then `import "server-only"`), except `db/schema.ts`, `db/seed-data.ts` and `db/vehicle-seed-data.ts`: drizzle-kit and Playwright read those outside Next.js, so `schema.ts` imports app code with `import type` only. `e2e/server-boundary.spec.ts` fails if database code reaches the browser's files.
  - Public reads use `'use cache'` with `cacheTag("<name>")` and `cacheLife("max")`, so pages stay prerendered (`○ /en`). A save calls `updateTag("<name>")`, which works only inside a Server Action. Use Drizzle's query builder: on the shared `Database` type, `db.execute()` returns `unknown`.
  - Saves call `authorize(permission)` or `authorizeUser()` first ("Roles and access" below; login-time writes are the exception), then check their input (a domain function such as `checkGarage`, returning problem codes), write in one transaction, and catch nothing. Tasks 28 and 40 are the first to call `saveGarage`, from a Server Action.
  - Changing the schema: edit `src/server/db/schema.ts`, run `npm run db:generate -- --name=<what_changed>`, commit the `.sql` file and `meta/` with the schema change, and restart `npm run dev` to apply it. Never edit a merged migration: write a new one. If an unmerged migration of yours went wrong, fix it, then `npm run db:reset`.
  - Never two processes on `.pglite/`: PGlite has one connection, and a second opener corrupts the folder. `npm run dev` is not always one process: when a cached read takes over 10 s, Next.js re-runs it in a helper process (its use-cache probe, a jest-worker child) to look for a deadlock. Two guards, in `src/server/db/`:
    - The lock (`folder-lock.ts`): `createDatabase` creates `.pglite.lock` with the `wx` flag, holding its process id and a random token. Another running process that tries gets a clear "already open by process N" error; a lock left by a process that has stopped is taken over; `closeDatabase` and process exit remove it.
    - Helper processes never open the folder (`openForThisProcess`, recognised by `isNextHelperProcess()`): their `getDatabase()` never settles. A probe that *fails* counts as "completed" and Next.js turns the real request into a deadlock error (a 500, seen in task 14); a probe that hangs runs into its time limit, counts as "inconclusive", and the real request goes on. Check this after a Next.js upgrade: it reads Next.js's helper entry script (`jest-worker/processChild.js`).

Money is integer paise. Text people read is `LocalizedText` in a jsonb column. Names are snake_case, written on each column.
  - Time: code that needs "now" takes a `Clock` (`@/lib/clock`, `systemClock` by default; tests pass `fixedClock(...)`). Never read the time while a prerendered page renders.
  - Settings: `APP_ENV` (`local` by default, `staging` or `production`) and `DATABASE_URL` are read through `serverEnv()` (`src/server/env.ts`). Staging and production refuse to start without `DATABASE_URL`, and on Vercel `APP_ENV` can't be `local`. Error messages name a variable, never its value. A URL postgres.js can't read (an unencoded `/`, `?` or `#` in the password) fails with a fixed message: Node's `TypeError` would carry the whole URL in its `input` (`postgresClient` in `src/server/db/index.ts`).

Open one database per file in `beforeAll`, reset its rows in `beforeEach`, and `closeDatabase` it in `afterAll`.

A redirect inside `<Suspense>` happens in the browser with status 200, which is why the proxy answers the common cases first with a real 307 ("Roles and access").

- **Roles and access** (task 16; plan `document/plans/2026-10-28-1836-feat-roles-access-plan.md`):
  - What each role may do lives in one table, `src/domain/permissions.ts`: `can(role, permission)`. Pages, actions and the data-access layer ask about a permission (`"garage.edit"`), never about a role: no code outside `permissions.ts` and `roles.ts` compares roles. To change who may do what, change the table and the copy in `permissions.test.ts` together. A new permission names the task that first uses it. Data a customer owns (their vehicles, their bookings) isn't a permission: the rule is "logged in, and the row is yours", in the query.
  - The owner is whoever logs in with `OWNER_PHONE_NUMBER` (`serverEnv()`; locally the garage's own number, required on staging and production). `effectiveRole` (`src/domain/roles.ts`) applies the rule on every session read (`getCurrentUser()`), and `syncOwnerRole` (`src/server/dal/users.ts`) writes it into `users.role` at each login, after the consents. Changing the setting moves owner access once it's live: `serverEnv()` reads settings once per process, so change it, then redeploy (or restart). From then on a stored `owner` on another number reads as `customer`, even inside an open login. `users.role` is only a hint: it's brought in line at each login, so it goes stale for anyone who doesn't log in again (a lost SIM never does). Code that reads another user's role (the team list, reports) passes each row through `effectiveRole(row.role, row.phoneNumber, serverEnv().ownerPhoneNumber)` and never filters on `role = 'owner'` in SQL. Nothing from a browser ever sets a role. Mechanics and managers are set by the owner (task 29).
  - Checks, in `src/server/auth/access.ts`:
    - Pages and Server Actions: `requireUser(locale)` (nobody logged in: a redirect to `/login?session=ended`, replacing the history entry) and `requirePermission(locale, permission)` (logged in without it: the 404 page; `forbidden()` is still experimental in Next.js 16.4.3). Both read the session, so in a page they sit inside `<Suspense>`, where the redirect happens in the browser and the 404 page answers status 200 with `noindex` (`node_modules/next/dist/docs/01-app/02-guides/streaming.md`, "Status codes"): a browser test checks the page shown, not a 404 status. A Server Action that needs a login calls `requireUser(locale)` first (the login actions themselves can't), and never reads a role or a user id from its form data.
    - The data-access layer: every function that isn't a public cached read checks who is asking on its first line, before it checks its input, calls `getDatabase()` or opens a transaction. Staff work calls `authorize(permission)`. A customer's own data (their vehicles, their bookings) calls `authorizeUser()` (logged in is enough: customers hold no permission) and filters the query by the returned user's id, never a user id from its caller. Both throw `AccessDeniedError` (a reason and the permission, nothing personal). Three kinds of function don't check, by design: public reads, cached or live (`readGarage`, `readAvailableSlots`: anyone may see them, and a cached one can't read the session anyway); writes made during a login, before a session exists (`login-codes.ts`, `consents.ts`, `users.ts`: only the login service calls them, and nothing in them comes from a browser); and functions that take the caller's transaction (`reserveSlot`, `releaseSlot`, `moveSlot`). For those, the function that opens the transaction (a booking save, task 23; cancel or reschedule, tasks 25 and 27) calls `authorizeUser()` or `authorize()` *before* it opens it: a session read inside the transaction would wait forever on PGlite ("Booking slots" below).
  - The proxy (`src/proxy.ts`, `src/lib/access-routes.ts`) only looks for the session cookie, never the database: a logged-out GET of a protected path (`PROTECTED_PREFIXES`, `/account` today; task 26 adds `/admin`) gets a 307 to `/login`, and a logged-in `/login` a 307 to `/account`. Form posts (Server Actions) are never redirected. The pages still check: a leftover cookie whose session is gone passes the proxy, the page sends the visitor to `/login?session=ended`, and the proxy lets that through, so it can't loop. The cookie names are checked against Better Auth's own `getSessionCookie` in a test (importing `better-auth/cookies` into the proxy would load its crypto on every request).
  - Tests: a page or action that needs a permission gets a test for "logged out" (the redirect), "wrong role" (the 404, or `AccessDeniedError` in the data-access layer, before `getDatabase` is called) and "allowed". Browser tests read a 307 with `page.request.get(path, { maxRedirects: 0 })`.
- **Vehicle catalogue** (task 17; plan `document/plans/2026-10-28-1802-feat-vehicle-catalogue-plan.md`):

- **Booking slots** (task 22; plan `document/plans/2026-10-28-1754-feat-slot-engine-plan.md`):
  - A slot is the time one vehicle reaches the garage. Slots start on whole multiples of the slot length after India midnight (on the hour for 1-hour slots), inside the day's hours. The rules are one `slot_rules` row: its CHECKs repeat `SLOT_RULE_LIMITS` (`database.test.ts` keeps them in step). Capacity 2 is a placeholder until the owner gives the number (`ownerSlotRules` in `seed-data.ts`). Closed dates (festivals) are `calendar_exceptions` rows; places taken are `slot_counters` rows, one per slot start, created on the first reservation.
  - Only `reserveSlot`, `releaseSlot` and `moveSlot` (`src/server/dal/slots.ts`) change a counter. Each counter change is one statement whose `WHERE` re-checks the limit, so two bookings can't both take the last place (`moveSlot` makes two such changes, which is why it needs a transaction). They take the caller's booking transaction as `db` (required): a booking and its place are saved or rolled back together. Never call `getDatabase()`, `readGarage()` or `readAvailableSlots()` (each opens its own) while that transaction is open (PGlite waits forever).
  - Order: reserve (or move) before the transaction's other writes and return a non-ok answer at once; write the booking only after an ok. Any change to an existing booking's place (cancel, reschedule, deleting a customer's data) first locks the booking row (`select ... for update`) and reads its slot and status from that row; only then release or move, then write the booking. Without the lock, two changes at once both give the old slot's place back. `moveSlot` takes a transaction only (its type has no bare-database form), reserves the new slot before releasing the old one, and treats a move to the same slot as a no-op. A release with nothing taken throws: the counters and bookings disagree.
  - "Full", `not-a-slot`, `closed-date` and `outside-window` are returned answers, never errors, so callers need no `catch`.
  - Slot reads are live: never `'use cache'` them. `readAvailableSlots` reads the clock before its first query, so call it at request time inside `<Suspense>`, after `await io()` (from `next/cache`).
  - Dates are India dates, `"YYYY-MM-DD"`, from `src/domain/india-time.ts`, never the UTC date (from 18:30 UTC it's already tomorrow in India). Counts are keyed by `startsAt.getTime()`, never by `Date` objects.
  - Tests: PGlite runs one query, or one whole transaction, at a time. A parallel-reservation test must call the bare test database: a transaction per call runs them one after another and hid a read-then-write bug in task 22. It still can't prove the real row race; task 20 does that on Postgres. Reset the rules with `delete(slotRules)` then `seedSlotRules(db)` (separate from `seedGarage`).

Don't approve one unless something is actually broken without it. `unrs-resolver`, `fsevents`, next-intl's `@swc/core` and `@parcel/watcher`, and esbuild (three copies, through drizzle-kit) are left unapproved; `check` and `test:e2e` pass without them. `npm audit` reports 4 moderate findings, all one esbuild dev-server advisory reached through drizzle-kit, which doesn't run that server, plus 3 low ones from a deepmerge advisory through the shadcn CLI (in the backlog). ## Task workflow: the Compound Engineering loop (always follow)

Every task goes **plan → work → review → compound**, inside our task and branch rules. Compound Engineering commands are namespaced: `/compound-engineering:ce-plan`, shortened to `ce-plan` below.

1. **Split the work into small tasks.** One task = one focused change that can be reviewed in about 15 minutes. If a request is bigger, split it (use the `task-planner` agent), add every piece to `document/task/task.md` with a step list, and show the plan to the user before starting.
2. **Name the task `NN_short_name`**: next free two-digit number, lowercase, words joined with `_`, two to four words that describe the outcome (`03_skills_installation`, `12_booking_form`).
3. **Branch name = task name.** Start from an up-to-date `main`: `git switch main`, then `git switch -c NN_short_name`.
4. **Track progress in `task.md`**: set the row to `In progress` when you start, tick each step only after it's really done, and link the learning doc. `Done` and the "Merge" tick come last, after the merge (step 11).
5. **Read past lessons.** Search `document/solutions/` for lessons that touch this task (`grep -ril "<topic>" document/solutions/`) and follow them.
6. **Plan.** For anything bigger than a one-file change, run `ce-plan` (run `ce-brainstorm` first if the request is still fuzzy). The plan is saved in `document/plans/`; link it from the task's steps in `task.md`.
7. **Work.** Build it, by hand or with `ce-work <plan file>`. Commit in small steps with Conventional Commit messages (see Git rules). When `ce-work` reaches its shipping step, it only commits on the task branch and stops (see "Compound Engineering" rules).
8. **Write the learning doc** at `document/learning/NN_short_name.md` from `document/learning/TEMPLATE.md` (see Learning docs; the `learning-doc-writer` agent can draft it). In the same commit, link it in the task's `task.md` row and tick "Write the learning doc" (missed in tasks 11 and 12, both caught by `code-reviewer`).
9. **Review.** If the task changed code, run `ce-code-review` (it only reports), unless `ce-work` already ran it for this change. Then run the `code-reviewer` agent: it checks the repo rules and is the final gate. Fix every "must fix", **then** add the real verdict and what you fixed to the learning doc. Never write that a review (or test, or merge) happened before it did. See `document/solutions/conventions/run-commands-before-documenting-output.md`.
10. **Compound.** Ask: *"If this lesson weren't written down, would a future session repeat the mistake or redo the investigation?"* Mistakes the review caught are the usual source. If yes, run exactly `/compound-engineering:ce-compound mode:non-interactive depth:lightweight <one-line summary>` (never plain `/ce-compound`; see the privacy rule). It writes one lesson to `document/solutions/`. If no, skip it and say why in the learning doc.
11. **Hand over through a pull request, then mark it done.** The owner merges every task on GitHub (their choice from task 10 on; tasks 01–09 were merged locally with `git merge --no-ff`).
    - When the reviews, their fixes and the compound step are done, tell the owner the task is **ready**, ask, then push the task branch (`git push -u origin NN_short_name`) and open the pull request into `main` with `gh pr create` (the owner's choice from task 12 on). Then stop: never merge it yourself.
    - The owner merges a task's pull request once, only after that "ready" message (their choice on 2026-10-27, after tasks 10 and 12 were merged before their reviews and needed follow-up pull requests). If a branch was merged early anyway, push the rest and open a follow-up pull request.
    - After the owner merges it, sync: `git switch main && git pull --ff-only origin main`.
    - Mark it done in one bookkeeping commit, `docs(NN): mark task NN done`: tick "Merge into `main`" and set `Done` in `task.md` and in the learning doc's header. Make it the first commit on the next task's branch, so `main` only ever changes through pull requests. Never commit directly on `main`.
12. **One task at a time.** Don't start the next task on the same branch. If you find unrelated work, add it to the backlog in `task.md` instead of doing it.

## Learning docs

Every task gets one. The reader is a junior software engineer.

- **Answer three questions:** Why (the problem), What (files changed and why each exists), How (step by step, with the real commands and what each flag does).
- **Also include:** new terms explained in plain words, how to check it works, common mistakes, a short exercise, links to learn more.
- **Write plainly:** short sentences, explain every new term the first time, use everyday comparisons when they help. Use the real file paths and commands from the task.
- **Be honest:** if something went wrong or was skipped, say so and explain why.
- **Keep it short:** aim for one to two screens. Link to official docs instead of copying them.

## Git rules

- **Commit messages** use Conventional Commits: `type: what changed`. Types: `feat` (new app feature), `fix` (bug fix), `docs` (documentation), `chore` (tooling, config, dependencies), `refactor`, `style`, `test`. Add a scope in brackets when it helps: `docs(01): fix example`.
- **`feat` vs `chore`:** `feat` only for something a website visitor or garage user gets. Agents, hooks, skills, settings, config and dependencies are `chore` (this slipped in tasks 04 and 08).
- **Small commits:** code, docs and tracker updates usually go in separate commits, so each can be reviewed or reverted alone.
- **Never commit secrets.** API keys and tokens go in `.env` (ignored by git) or the tool's own login. Commit a `.env.example` with fake values instead.
- **Ask the user first** before: `git push`, opening a pull request, deleting a branch, `--force` anything, rewriting history on `main`, or installing anything globally (`-g`, `npm install -g`, `brew install`).
- **Don't commit generated folders** such as `node_modules/` or `.next/`. `.gitignore` already covers them.

## Agents

Subagents live in `.claude/agents/`. The main session runs the task workflow and owns git (branches, commits, merges); subagents do one focused job and report back.

| Agent | Use it when | Can change files? |
| --- | --- | --- |
| `task-planner` | New work might need more than one task | Only `document/task/task.md` |
| `ui-engineer` | A task changes how the app looks, feels or moves | Yes (app code); no git |
| `learning-doc-writer` | A task's changes are committed and need a learning doc | Only the learning doc |
| `code-reviewer` | A task branch is ready to merge | No (read-only) |
| `seo-reviewer` | Page files changed (the SEO hook asks automatically), or the owner asks to check SEO | No (read-only) |

Run independent subagents in parallel. When an agent's job changes, update its file and this table in the same task.

## SEO review

- **Automatic:** a Stop hook (`.claude/hooks/seo_check.py`, registered in `.claude/settings.json`) runs every time you finish a reply. If any file under `src/app/`, `src/components/`, `src/content/`, `src/i18n/`, `messages/` or `public/` changed since the last review (`src/app/api/`, `route.ts` files, tests and `.DS_Store` excluded), it sends you feedback once (shown as "Stop hook feedback") with a list of the changed files. It waits while a background subagent is still running, so half-built pages aren't reviewed.
- **When it asks:** run the `seo-reviewer` agent on the affected pages, **in the foreground** (not in the background, so it doesn't review half-finished pages while another agent is still building them). Then reply with a short **"SEO check"** section: what changed, each page's verdict (Pass / Needs work) and the suggested fixes. **Don't apply the fixes unless the owner asks.**
- **On demand:** when the owner asks to "check SEO" (for a page or the whole site), run `seo-reviewer` the same way.
- **Child sessions:** start every `claude -p` helper session with `GOMECHANIC_SEO_HOOK=off` in front (e.g. `GOMECHANIC_SEO_HOOK=off claude -p ...`). Otherwise the child takes the review, and the owner never sees it.
- **Re-review everything:** delete `.claude/.seo-reviewed.json` (git-ignored); the next reply reviews all page files. A fresh clone or worktree has no state file, so its first reply reviews every page once.
- **Two sessions in one folder** share the state file: the first one to finish a reply gets the review, even if the other made the change. Keep one session per checkout while building pages.
- **Before task 42:** missing metadata, sitemap, robots file and JSON-LD are planned for task 42, so the agent lists them on one "Waiting for task 42" line instead of failing the page.

## Definition of done

A task is done when all of these are true:

- [ ] The work is on its own `NN_short_name` branch, in small commits
- [ ] Bigger tasks have a plan in `document/plans/`, linked from `task.md`
- [ ] It works, and you checked it (ran it, tested it, or opened it)
- [ ] `npm run check` and `npm run test:e2e` pass (once the app exists, from task 09 on)
- [ ] If the task touched the design (tokens, `type-*`, `ui/` or `site/` components), its samples are on `/dev/design` and `npm run test:design` passes
- [ ] `document/task/task.md` has the learning doc linked and every step ticked except "Merge" (ticked by the bookkeeping commit in step 11)
- [ ] The learning doc exists and answers Why, What and How
- [ ] `readme.md` and `CLAUDE.md` are updated if the task changed how the repo works
- [ ] No secrets, no generated folders committed
- [ ] `code-reviewer` reports "Ready to merge" (or every "must fix" is fixed)
- [ ] The compound question was asked: a lesson is in `document/solutions/`, or the learning doc says why none was needed
- [ ] The task branch is pushed and the owner merged its pull request into `main`; the `docs(NN): mark task NN done` commit (first commit of the next task's branch) sets `Done`
